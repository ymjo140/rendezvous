# 4주차 — 재방문 측정과 운영 점검

기준: 3주차 PR #5 (`771b9ca`) 다음 개발 묶음. 이 변경은 RDV-10의 핵심 재방문 지표·운영 점검을 구현하고 RDV-11의 배포 확인 도구를 제공한다. 4주차 전체 또는 실사용 베타 검증이 완료된 상태는 아니다.

## 구현

- `/admin/beta`: 기존 운영 지표 화면에서 연결되는 관리자 전용 대시보드.
- `/api/admin/beta-metrics`: 기존 관리자 인증을 사용하고 개인·크루 식별자를 반환하지 않는다. 성공과 계산 실패 응답 모두 `Cache-Control: no-store`다. DB/스키마 문제는 503이며 0건으로 바꾸지 않는다.
- `/api/health/live`: 프로세스 응답, 앱 버전, 배포 커밋 확인.
- `/api/health/ready`: DB 질의와 2·3주차 필수 테이블/컬럼 조회 가능 여부 확인. 행 데이터는 읽지 않는다. 실패는 503이며 연결 정보·SQL 오류를 노출하지 않는다. RLS나 권한 감사 전체를 대신하지 않는다.
- 요청 로그: UTC 시각, 경로 템플릿, 상태, 지연, 예외 발생 여부를 남긴다. 토큰·본문·실제 방문 ID는 기록하지 않는다.
- 로그 집계 도구: 내보낸 로그에서 경로별 요청 수·실패율·p50/p95/p99를 계산한다. 5xx 또는 처리 예외를 실패로 집계한다. 로그를 내보낼 때 분석 시간 범위를 선택해야 한다.

## 지표 정의

| 지표 | 분자·분모와 기간 |
|---|---|
| 반복해서 모인 크루 | 한국 시간 오늘을 포함한 최근 28개 달력일에 인증 공동 방문이 2회 이상인 크루 수. 오늘은 조회 시각까지만 포함 |
| 방문한 크루 / 공동 방문 / 첫 방문 크루 | 같은 28일 범위의 방문 크루 수 / 방문 이벤트 수 / 생애 첫 인증 공동 방문을 한 크루 수 |
| 28일 내 두 번째 공동 방문율 | 생애 첫 인증 공동 방문 후 28×24시간이 지난 크루 중 그 기한 안에 두 번째 공동 방문을 한 크루의 비율 |
| 같은 가게 28일 재방문율 | 크루·가게별 첫 방문 후 28×24시간이 지난 쌍 중 그 기한 안에 다시 방문한 쌍의 비율 |
| 첫 방문 주차 | 한국 시간 월요일 시작. 최근 12개 첫 방문 주차를 표시하며 전체 재방문율은 관찰된 누적 코호트 기준 |
| 외부 리스트 담기 | 28일 내 `creditable=true`로 기록된 최초 복사 이벤트 수. 재복사 업데이트를 추가 성과로 세지 않음 |
| 후기 응답 | 28일 내 인증 공동 방문의 참가자가 남긴 설문 응답 수. 실제 재방문 수와 구분 |

`visit_service.verified_events`와 같은 인증 방문 원천을 사용한다. 개인 방문, 공동 방문 대기, 과거 자기 신고 체크인, 예약·결제·재방문 의향은 방문 지표에서 제외한다. 조회 시각보다 늦게 발생하거나 늦게 인증되는 방문도 제외한다. 경계 시각의 방문과 정확히 28일째인 재방문은 포함한다.

아직 28일이 지나지 않은 크루는 먼저 재방문했더라도 성숙 분모·분자에서 함께 제외한다. 분모가 0이면 `rate=null`, 화면은 **관찰 대기**다. 숫자가 있는 0%와 구별한다. 비공개 크루도 관리자 집계에는 포함하며 크루 이름·ID는 노출하지 않는다. 현재는 별도 모집 명부가 없으므로 파일럿 모집 크루만의 성과라고 해석하면 안 된다.

## 계산·화면 검증

전체 방문을 내려받거나 크루별로 API/쿼리를 반복하지 않는다. 윈도 함수와 집계로 크루 또는 크루·가게당 한 행만 반환하고 전체 계산은 6개 쿼리로 고정한다. 큰 운영 데이터에서의 성능은 별도 실측 대상이다.

새로고침과 인증 만료 시 이전 결과를 숨기고, 늦게 도착한 이전 요청은 폐기한다. 로딩·권한 거절·연결 실패·빈 관찰 상태를 구분한다. 이 화면은 기존 DAU API의 성공 여부에 의존하지 않는다.

회귀 테스트는 성숙/미성숙 혼합, 28일 경계 전후 1μs, 다른 가게 방문, KST 자정·주 경계, 미래 인증, 개인/과거 방문 제외, 일정한 쿼리 수, 관리자 권한, DB 실패, 준비 상태, 로그 통계, 배포 커밋 불일치를 다룬다. PostgreSQL CI에 실제 방문 인증 → 지표 집계 → 준비 상태 확인 테스트를 추가했다.

## 배포와 확인

이 4주차 변경에는 새 마이그레이션이 없다. 3주차 스키마가 먼저 필요하다.

2026-09-11 운영 Supabase에 `missions_feedback` 마이그레이션을 적용했다. 새 테이블 2개의 RLS 활성화와 anon/authenticated 직접 권한 차단을 확인했으며, 사용자 17명·크루 11개가 유지됐다. 3주차 PR #5는 사용자 명시적 승인 후 main 병합을 완료했다(`e86d21fd137914457dbc55b35a9f44b3186de652`). 이 커밋의 rendezvous·wemeet-project Vercel 배포도 성공했다.

4주차 변경은 `codex/week4-beta-metrics` 브랜치에서 main 대상 PR로 검증한다. 로컬 백엔드 137개, 링크 검사 4개와 프론트 lint/타입검사/프로덕션 빌드가 통과했다. PostgreSQL 11개를 포함한 CI 전체 성공을 병합 조건으로 삼고, 최종 검사·병합·배포 결과는 PR에 기록한다. 사용자 병합 승인은 이미 받았다. 적용 순서는 CI → 병합 → Render API/Vercel 배포 확인이다. Render는 `RENDER_GIT_COMMIT`, 다른 호스팅은 `APP_REVISION`에 배포 커밋을 지정한다.

```sh
python backend/scripts/check_deployment.py https://wemeet-backend-xqlo.onrender.com --expect-revision <배포한-커밋>
python backend/scripts/summarize_api_logs.py /path/to/render-log-export.jsonl
```

배포 검사는 GET만 사용한다. 두 상태 응답과 지정한 커밋이 일치해야 종료 코드 0이다. 구버전의 404, DB 미준비, 다른 커밋, 알 수 없는 커밋은 통과하지 않는다. 연결 요청별 제한은 10초이며 준비 상태의 DB 질의 제한은 각 3초다. DB 연결/풀 대기 제한 전체를 보장하는 것은 아니다. 리디렉션과 자격증명이 포함된 URL은 허용하지 않는다.

초기 수동 점검 기준: 배포 후 준비 상태 실패 또는 커밋 불일치는 배포 확인 실패, 5분 이상 구간에서 100건 이상인 경로의 5xx/예외 비율 1% 초과나 p95 2초 초과는 원인 점검 대상으로 삼는다. 제품별 정상 부하 실측 전 임시 기준이며 외부 알림 시스템을 연결한 상태는 아니다.

새 테이블은 서버 전용으로 RLS 정책 없이 클라이언트 접근을 막는 구조다. Supabase의 `RLS Enabled No Policy` 안내와 기존 테이블의 RLS 미설정 경고는 별개다. 새 스키마 적용이 기존 보안 미해결 사항까지 해결했다는 뜻은 아니다.
